### A1. ~~归档模式「只拉文字版」~~：**已实现（2026-11-06）**

> ① 回执不是「做好了」，而是 **状态行 + 完整文字稿**（超 3000 字即 3 条容量，按句子边界截断，

> ③ 归档也在**回复层**走限流与拆分（最多 3 条），不再"只回一句、不贴正文"。
> 下面保留当时的方案原文，作历史记录。

**一句话**：@ 里带关键字「只拉文字版」时，只把**完整口播文字**拉下来存本地，
B 站回状态行 + 文字稿前 3000 字。**全程不调用大模型，0 token。**

#### 方案（已确认，不要再改设计）

| 环节 | 规则 |
|---|---|
| **触发** | **只认 @ 正文里的关键字「只拉文字版」**。正则匹配，**代码写死，不进模型层**。没有这个关键字就绝不走本分支 |
| **产物** | 完整视频口播内容（字幕全文 / OCR 全文），**原样落本地**，一个大模型 token 都不花 |
| **成功回执** | 回一句 **「做好了」** |
| **失败回执** | 回 **「失败：〈原因短语〉」**，原因由**代码**给出（如"没拿到字幕"、"OCR 抽帧失败"），**不过模型** |
| **其他说明** | **不附加任何说明**。不加"总结已生成"、不加链接、不加字数 |
| **正文是否发评论** | **不发**。几万字口播装不进 B 站 1000 字上限，只落本地文件 |

## B. 有意不做

### B1. 私信通道
- **原因**：需求已撤销。私信是"人对人"通道，用做视频总结等于骚扰，且需要互关。

### B2. 图文 / 动态（opus）
- **原因**：接口匿名回 `-101 账号未登录`，必须登录；且内容是长图 + 长文，管线与视频完全不同。

### B3. 「长图滚动」的全文还原（滚动拼接）
- **现状**：只做「多帧 OCR + 行级去重 + 断行拼接」的简单版，已能覆盖
- **原因**：不需要像素级拼接——滚动单调，文本顺序即阅读顺序
- **再做条件**：日志里出现"OCR 文本明显断裂/重复"的样本且占比 >10%

### B4. 多轮对话（>1 次追问）
- **现状**：每个 bvid 一个 DSH 会话（`--session-id`），追问天然共享上下文
- **待观察**：会话会累积，长视频多次追问后 token 成本会涨

### B5. 人设 / 日记 / 随机开摆 / 沉默衰减
- **原因**：定位是工具，不是活鱼。人设会让总结变形并掩盖质量退化。

### B6. 举报 / 点赞 / 投币 / 关注
- **原因**：只做总结，不做互动。少一个写接口就少一份风控风险。

### B7. 分区（tname）筛选
- **原因**：实测 `view.tname` / `tname_v2` 在 4/4 样本里都是空字符串，靠它筛分区等于没筛。

### B8. 雪碧图 OCR 当正文
- **原因**：实测字数准、字全错（"中共中央政治局委托"被识别成"义受中央政治商委托"）。
  雪碧图只做探针，正文必须来自 1080P 抽帧。

### C1. ~~ASR 那条腿（M4）~~ —— 2026-11-06 已实现
- 实现：`lib/asr.mjs` + `python/asr.py`，只下 DASH 音轨（`fnval=16`，1-2MB）→ faster-whisper

### C3. 多平台适配（2026-11-06 记，**先不做**）
- **动因**：用户提到后续可能接 B 站以外的平台（YouTube / 抖音 / 小红书）
- **结论**：结构上能支持，但"被 @ 当评论区分析师"这个形态**只有 B 站天然成立**
- **要做的话**，先把这些抽成 `platform` 适配器接口：
  ```js
  { name, 解析ID, 拉召唤, 取元信息, 取字幕, 下载视频/取音轨, 发回复, 限额:{单条字数, 最多几条} }
  ```

  平台无关的（compose / routing / store / runs / web）直接复用；
  B 站实现挪到 `platform/bilibili.mjs`（现在散在 bili/feed/media/ocr/asr/reply 里）
- **工作量**：抽象 + 搬家约半天到一天

  | 小红书 | ❌ | 需签名 + 风控 | ❌ 更弱 |

- **替代形态**：别的平台更现实的是"给链接就产出"（网页输入框），而不是召唤型

## E. 长期规划
### E1. 知识库：语义检索"我刷过什么"（2026-11-06 用户提出，**很后期**）
**用户原话**：以后想到某个问题，能清楚检索到我刷过哪些文章、看过哪些视频。初步想法是用向量类似的算法做检索。

**现状盘点**（决定什么时候才值得做）：
- 数据源只有 `runs/<时间>-<BV>/transcript.txt`（视频文字稿）+ `summary.md`
- **目前只有 8 条**，一天刷 10 条一年才 3650 条
- 每条 3000-20000 字 → 一年约 1000 万～7000 万字

**三个技术选项**：

| 方案 | 依赖 | 中文难点 | 何时够用 |
|---|---|---|---|
| **A. SQLite FTS5**（关键词/二元分词） | 零依赖（`node:sqlite` 内置） | 要自己做 bigram 分词 | 几百条以内基本够 |
| **B. 本地 embedding**（bge-small-zh onnx） | 模型几百 MB + 计算 | 中文模型成熟 | 上千条、且 A 漏检明显时 |
| **C. 混合**：FTS5 粗排 + embedding 精排 | B 的全部 | — | 上万条 |

**初步判断**：
- **真正的成本不在向量，在数据接入**：哪些来源（只有 B 站？公众号/知乎/网页？）、怎么清洗、怎么去重、chunk 怎么切
- 视频文字稿是**口语、碎片、无标点**，chunk 策略比 embedding 模型更影响效果
- 建议路线：**先 A（当天能做完）→ 数据量破几百且发现漏检严重 → 再上 B**

**待定**：见 D2 的 Q（数据源 / 用途是"找到"还是"问答" / 规模预期）

### E2. 记忆（2026-11-06 澄清：这是**经验记忆**，不是知识库）

**用户原话（两次）**：
1. 「类似 Skills 之类的，聊到某个问题的时候激活加载，像人类一样；但担心"做成 skill 会不会太多了"」
2. 「我希望的记忆其实不是只把这个视频观看的框架接入，而是后续能够让你这个 AI 运行的时候稍微带有一点原来做过东西的记忆。所以可能并不局限于语言」

**关键澄清**：用户要的**不是**「能搜到我刷过什么」（那是 E1 知识库），
而是**「这个 AI 下次跑的时候，隐约记得自己以前干过什么」** —— 经验/情节记忆。

### 三类记忆，必须分开做

| 类型 | 内容 | 谁产生 | 检索方式 | 对应 |
|---|---|---|---|---|
| **知识记忆** | 看过的视频/文章正文 | 外部内容 | 文→文 | E1 知识库 |
| **用户记忆** | 姓名/经历/偏好/技能栈 | 用户自述或抽取 | 关键词/向量 | 原 E2 设想 |
| **经验记忆** | **它自己做过什么、结果如何** | 系统运行 | 结构化过滤 + 语义 | **用户真正想要的** |

三类可以共用一套存储与检索，但**注入时机和策略完全不同**：
- 知识记忆：用户提问时检索（被动）
- 用户记忆：几乎每轮都该带（长期稳定）
- **经验记忆：只在"这件事以前发生过"时检索（条件触发）**

### 「不局限于语言」意味着什么

记忆条目的载荷可以不是文本：

| 载荷 | 例子 | 检索方式 |
|---|---|---|
| 文本 | 上次给这个视频写的看法 | 全文/向量 |
| **结构** | 这条视频走了 asr 通道、耗时 250s、用户没点赞 | SQL 过滤（最实用） |
| **画面** | 第 3 分钟那页 PPT 的样子 | 图像向量（CLIP 类） |
| **音频** | 这个 UP 的声音特征 | 声纹向量 |
| 引用 | 指向 runs/<id>/ 的指针 | 直接读文件 |

**注意**：真正的跨模态检索（用文字搜图片）成本远高于结构化过滤。
**这条鱼 90% 的"经验"用 SQL 就能表达**（哪条视频、什么档、多久、成没成），
先别上 CLIP。

### 现成的基础（已经有一半了）

系统里其实已经在记经验了，只是**没有检索和注入**：

→ **缺的只有两件事：① 一个能查的索引 ② 在 prompt 里注入的时机与格式**

### 实现骨架（很后期，先记着）

```
episodes 表（SQLite）
  id | at | bvid | up_mid | up_name | tier | mode | source | quiet
     | chars | needSplit | ok | issues | ms | tokens | 用户反应
  载荷列：text（可空）| frame_path（可空）| audio_path（可空）| embedding blob（可空）

检索：
  episode_search({ up_mid?, tier?, ok?, since?, query? })
    → 先 SQL 过滤（结构化条件最有效）
    → 再对 text 做 FTS5 / 向量（可选）

注入（关键，错了会污染判断）：
  只在两种情况下注入：
    ① 同一 UP 的历史档位（"这个 UP 上次字幕是歌词，已跳过"）
    ② 同一视频的历史（"这条 3 天前处理过，当时走了 asr"）
  其余一律不注入 —— 无关经验比没有经验更糟
```

### 为什么"做成 N 个 skill"是错的

DSH 的 skill 机制是「描述列表 + 按需加载」。**几百条记忆 = 几百个 skill 描述**，
光描述就能把上下文撑爆，模型在几百个里选还会选错。

正确形态：**1 个 skill + N 条数据 + 1 个检索工具**
```
skill: memory（只有这一个）
  描述："当用户提到过去的事，或要处理一个见过的 UP，调用 memory_search"
数据：episodes 表（N 条）
工具：memory_search(query, filters) → 相关几条
```

### 风险（有数据）

- `MemoryAgentBench`：纯长上下文 42.2，MemGPT 28.3、Zep 24.0、Mem0 21.1 ——
  **小规模下记忆机制是负收益**
- 注入错误经验比不注入更糟：模型会把"上次这个 UP 的字幕是歌词"当成事实，
  哪怕这次字幕是正常的
- 所以注入必须**带条件、带时间、带不确定度**，不能当成事实陈述

### 待定（用户研究后拍）
- 经验记忆写入是自动（每次跑完自动写一条）还是手动
- 遗忘策略：按时间衰减？按 UP 聚合？还是只保留最近 N 条
- 是否要跨项目共享（鱼的运行经验，和学习工作区的经验要不要打通）


## F. 记忆组件调研结论（2026-11-06，60 个项目实测）

> 完整报告：`D:\00000\aiStudy\肥鱼视频阅读\docs\记忆组件调研.md`（1034 行）
> 八份方向草稿：`D:\00000\aiStudy\肥鱼视频阅读\docs\memory-research`
> **本段只抄结论，选型由用户读完原文自己拍。**

### 一句话结论

**记忆层用 MemOS 本地插件（npm + 单 SQLite + MCP），档案类用 Markdown 文件。**
分工：会变的结构化事实（姓名/住址/经历/技能栈/偏好）进 SQLite；要投递、要 review 的文档进 Markdown。
判断标准只有一条：**删掉索引，知识还在不在？**

### 最扎心的实测数据（决定"先别上重型方案"）

`MemoryAgentBench`，同一个 GPT-4o-mini 底座：

| 方案 | 分数 |
|---|---|
| 纯长上下文 FullMemory | **42.2** |
| MemGPT | 28.3 |
| Zep | 24.0 |
| Mem0 | 21.1 |

`MemBench` 在 10k 条规模下同样：MemoryBank 0.442 / MemGPT 0.455 / SCMemory 0.355，**全输给 FullMemory 0.647**。

→ **数据量不够大时，记忆机制是负收益。** 单人助手是几百到几千条，重型方案解决的是多租户/分布式/权限治理，不是你的问题。

### 三层方案的成本量级

| 层 | 方案 | 磁盘 | 运行算力 | 首次接入 | 外部依赖 |
|---|---|---|---|---|---|
| 检索 | **SQLite FTS5 + trigram** | 索引≈原文 2-4 倍（3650 条约几百 MB） | 查询毫秒级 | **半天** | **零**（`node:sqlite` 内置） |
| 检索 | **向量（LanceDB / sqlite-vec）** | 向量库 ≈ 原文 1-2 倍 + 模型几百 MB | 建索引一次；查询毫秒级 | **2-3 天** | 本地 embedding 模型（bge-small-zh 等） |
| 记忆层 | **MemOS 本地插件** | 单 SQLite 文件 | 每次写记忆要调 LLM 抽取 | **3-5 天**（含设计"记什么") | Node 22+；服务端版还要 Neo4j+Qdrant（**别碰**） |

关键：**第 2、3 层的钱不在磁盘和算力，在"设计"**——记什么、什么时候忘、改口了怎么办。这三件事没有一个开源项目替你做（`MemoryAgentBench` 里"多跳选择性遗忘"所有方法 ≤28%）。

### 唯一把"遗忘"做对的

`graphiti` 的双时态（`valid_at/invalid_at` + `created_at/expired_at`）——写入时就地判矛盾、**软失效而非删除**。代价：硬依赖 Neo4j/FalkorDB，Windows 上基本等于必须 Docker。

### 名单和现实不符的（实测，别被旧资料误导）

| 以为 | 实际 |
|---|---|
| `getzep/zep` 是 Zep 产品 | README 明写 "not Zep's product"，只剩示例；内核在 `getzep/graphiti` |
| `letta-ai/letta` 活跃 | 已迁 `letta-ai/letta-code`，25,362★ 的主仓是空壳 |
| LangChain 有 memory 模块 | v1 已移除，`libs/langchain/` 现在装的是 `langchain-classic` |
| AutoGen 仍在维护 | 2026-10-28 **已归档** |
| `claude-mem` 是文件方案 | 核心是 SQLite + Chroma + Worker 进程 |
| chroma 嵌入式 | 嵌入式只对 **Python** 成立，npm 包是纯 REST 客户端 |

### 落地建议（三阶段）

1. **先 FTS5**（半天）：把 `runs/*/transcript.txt` 灌进 `node:sqlite` 的 FTS5，`tokenize='trigram'`，做 `fish search "关键词"`
2. **真需要语义检索了**再加向量（LanceDB 或 sqlite-vec）——**几千条以内暴力算余弦就够，不需要任何向量库**
3. **只有当"事实会变、要跨会话记住用户"成为真痛点**，才考虑 MemOS 这类记忆层
