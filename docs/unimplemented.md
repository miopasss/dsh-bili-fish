## A. 已排期（A1 已完成，A2 待做）

### A1. ~~归档模式「只拉文字版」~~：**已实现（2026-11-06）**

> **已实现**，见 `lib/routing.mjs` 与 `bin/fish.mjs` 的 `--mode archive`。
> 与下面 2026-11-04 的方案相比，用户 2026-11-06 重新定了三处，以**新行为**为准：
> ① 回执不是「做好了」，而是 **状态行 + 完整文字稿**（超 3000 字即 3 条容量，按句子边界截断，
>    末尾注明「全文已存本地，评论区只贴前 N 字」）；
> ② 触发词由 `lib/routing.mjs` 统一解析（`只拉文字版`，2026-11-06 收词时把「归档模式」同义词删了），CLI 也可 `--mode archive`；
> ③ 归档也在**回复层**走限流与拆分（最多 3 条），不再"只回一句、不贴正文"。
> 下面保留当时的方案原文，作历史记录。

**一句话**：@ 里带关键字「只拉文字版」时，只把**完整口播文字**拉下来存本地，
B 站回状态行 + 文字稿前 3000 字。**全程不调用大模型，0 token。**

#### 方案（已确认，不要再改设计）

| 环节 | 规则 |
|---|---|
| **触发** | **只认 @ 正文里的关键字「只拉文字版」**。正则匹配，**代码写死，不进模型层**。没有这个关键字就绝不走本分支 |
| **产物** | 完整视频口播内容（字幕全文 / OCR 全文），**原样落本地**，一个大模型 token 都不花 |
| **成功回执** | 回一句 **「做好了」** |
| **失败回执** | 回 **「失败：〈原因短语〉」**，原因由**代码**给出（如"没拿到字幕"、"OCR 抽帧失败"），**不过模型** |
| **其他说明** | **不附加任何说明**。不加"总结已生成"、不加链接、不加字数 |
| **正文是否发评论** | **不发**。几万字口播装不进 B 站 1000 字上限，只落本地文件 |

#### 与大模型模式的分工

| | 默认模式 | 归档模式（本条目） |
|---|---|---|
| 触发 | 任何 @ | @ 里含「只拉文字版」 |
| 处理 | 字幕/OCR → 喂模型 → 一段正文 | 字幕/OCR → **直接落盘** |
| token | 约 1 万 | **0** |
| 回执 | 一段正文（超 1000 拆两条） | 「做好了」 |
| 产物 | summary.md | transcript.txt（完整口播） |

#### 实现要点（将来做的时候看这里）

1. `bin/fish.mjs` 里加分支：命中关键字 → 走 `transcript` 的那条路（已有 `acquireMaterial`），**跳过 compose/model**
2. 回执文案是**常量**，不拼模型输出
3. 失败原因用**固定短语表**（与错误码对应），别让代码临时造词
4. `runs/index.jsonl` 增加 `mode: 'archive' | 'opinion'` 字段，便于统计
5. 不需要改 `compose.mjs` 的自检（因为根本不走生成层）—— 这一点比原先估计的更简单
6. 工作量：**约 0.5 天**（不含回复层接线 M3）

#### 依赖

必须先有 M3（回复到 B 站）。在那之前这个分支只能在本地跑出文字稿，无法"回一句做好了"。

### A2. 后端统计页面（用户 2026-11-04 提出，明确要求先不做）

**要什么**：一个本地 Web 页面，能看到"我一共问了几次 / 问了哪些视频 / 每次用了什么素材 / 花了多少 token"。

**数据基础已经就位**：`lib/runs.mjs` 每次运行都会往 `~/.dsh/bili-fish/runs/index.jsonl` 追加一行，
`stats()` 已经能算出总数、按天分布、按素材类型分布、累计字数与 token。

**为什么要先不做**：属于"界面"，会引入 HTTP 服务、前端资源和信任栅栏（DSH 的 Web 端口是回环地址，
但浏览器里任何网页都能向回环发请求，不设栅栏等于把本地数据开放给任意页面 —— 参考 whale 的
`connection.requestRejection` 做法）。等 M2/M3 跑起来、数据积累到有意义再一起做。

**最小可行形态（将来）**：
- `node bin/fish.mjs stats` —— 命令行版，先看数字
- `node bin/fish.mjs serve --port 87xx` —— 只监听 127.0.0.1，带一次性 token
- 页面只读，不做任何写操作

## B. 有意不做

### B1. 私信通道
- **原因**：需求已撤销。私信是"人对人"通道，用做视频总结等于骚扰，且需要互关。

### B2. 图文 / 动态（opus）
- **原因**：接口匿名回 `-101 账号未登录`，必须登录；且内容是长图 + 长文，管线与视频完全不同。

### B3. 「长图滚动」的全文还原（滚动拼接）
- **现状**：只做「多帧 OCR + 行级去重 + 断行拼接」的简单版，已能覆盖
- **原因**：不需要像素级拼接——滚动单调，文本顺序即阅读顺序
- **再做条件**：日志里出现"OCR 文本明显断裂/重复"的样本且占比 >10%

### B4. 多轮对话（>1 次追问）
- **现状**：每个 bvid 一个 DSH 会话（`--session-id`），追问天然共享上下文
- **待观察**：会话会累积，长视频多次追问后 token 成本会涨

### B5. 人设 / 日记 / 随机开摆 / 沉默衰减
- **原因**：定位是工具，不是活鱼。人设会让总结变形并掩盖质量退化。

### B6. 举报 / 点赞 / 投币 / 关注
- **原因**：只做总结，不做互动。少一个写接口就少一份风控风险。

### B7. 分区（tname）筛选
- **原因**：实测 `view.tname` / `tname_v2` 在 4/4 样本里都是空字符串，靠它筛分区等于没筛。

### B8. 雪碧图 OCR 当正文
- **原因**：实测字数准、字全错（"中共中央政治局委托"被识别成"义受中央政治商委托"）。
  雪碧图只做探针，正文必须来自 1080P 抽帧。

## C. 待评估

### C1. ~~ASR 那条腿（M4）~~ —— 2026-11-06 已实现
- 实现：`lib/asr.mjs` + `python/asr.py`，只下 DASH 音轨（`fnval=16`，1-2MB）→ faster-whisper
- 触发：判定为 `asr`，或 OCR 读到的字 < `asr.ocrFallbackMinChars`（默认 80）
- 强制指定（`用字幕`/`用OCR`/`用ASR`）时不降级，走不通就如实报错
- 已知代价：中文专业词会错（实测「函数」→「寒树」），要更准就换 `medium`/`large-v3`
- ⚠️ 依赖坑：`av` 必须 `<14`，否则 faster-whisper 转写时抛 `metadata_errors`

### C2. 时间戳粒度
- OCR 路径的时间戳精度 = 抽帧间隔（默认 5s），长视频放宽到 8s
- 若日志显示"时间戳指错位置"的反馈增多，再考虑对"翻页点"做加密抽帧

### C3. 多平台适配（2026-11-06 记，**先不做**）
- **动因**：用户提到后续可能接 B 站以外的平台（YouTube / 抖音 / 小红书）
- **结论**：结构上能支持，但"被 @ 当评论区分析师"这个形态**只有 B 站天然成立**
- **要做的话**，先把这些抽成 `platform` 适配器接口：
  ```js
  { name, 解析ID, 拉召唤, 取元信息, 取字幕, 下载视频/取音轨, 发回复, 限额:{单条字数, 最多几条} }
  ```
  平台无关的（compose / routing / store / runs / web）直接复用；
  B 站实现挪到 `platform/bilibili.mjs`（现在散在 bili/feed/media/ocr/asr/reply 里）
- **工作量**：抽象 + 搬家约半天到一天
- **真成本在平台差异，不在代码**：

  | 平台 | 字幕 | 发评论 | @ 召唤成立吗 |
  |---|---|---|---|
  | B站 | ✅ AI 字幕 API | 签名简单（csrf） | ✅ msgfeed 有 @ 消息 |
  | YouTube | ✅ timedtext | Data API 要 OAuth | ⚠️ 有 @ 但不形成召唤流 |
  | 抖音 | ❌ | `a_bogus` 签名，风控极严 | ⚠️ 门槛高 |
  | 小红书 | ❌ | 需签名 + 风控 | ❌ 更弱 |

- **替代形态**：别的平台更现实的是"给链接就产出"（网页输入框），而不是召唤型

### C4. 静默模式（2026-11-06，见下）—— 本轮要做，不在这
